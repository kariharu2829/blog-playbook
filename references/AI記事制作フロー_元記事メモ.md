# 記事制作のAI分担の参考メモ：「コピペでマネできるClaude Code×ブログ記事制作」

ステップ3〜5（記事ごとの層）の骨格と、AIと人の役割分担の根拠にした外部ノウハウの要点。原文の転載ではなく要約。配布プロンプト3本は筆者が「コピペで真似してよい」として公開したもので、要旨を保存する。
出典: リベシティ ノウハウ図書館 https://library.libecity.com/articles/01M0RJXEBMDYVQB9WN00AK35QS （2026-09 読み込み）
筆者の環境: Claude Code、スプレッドシート（API）、ラッコキーワード（API・スタンダード）、Search Console（API）、Claude in Chrome

## 結論
- 「〇〇について記事を書いて」の丸投げでは読まれない・稼げない記事になる。逆に自分で全部やると時間で負ける
- **自分で考えながら、AIを仕組み化して育てる**
- 仕組み化＝作業の手順書をファイル（スキル）にしてAIに覚えさせる。次回から一言で同じ作業を再現できる。「考える・迷う」時間が減り、自分がやるべき作業に集中できる

## 記事作成ルーティン10ステップ（全部スキル化）
| # | 工程 | 誰が |
|---|---|---|
| 1 | キーワード・競合リサーチ | AI |
| 2 | 記事構成のスプレッドシート作成 | AI |
| 3 | 記事構成の最終判断 | **人** |
| 4 | 本文執筆・WordPress入稿 | AI |

| 9 | 公開 | **人** |

人がやるのは「今日は〇〇というKWで記事作成いくよ」と伝えること、構成の最終判断、公開の判断。

## AIに任せてよかった4つ
1. **事前リサーチ（スプレッドシート化）**：KW収集（サジェスト・関連語・共起語・質問系＋検索ボリューム）、検索意図の深掘り（顕在ニーズ・潜在ニーズ・読者のゴール）、競合上位10サイトのタイトル・見出し分析、タイトル10案、H2/H3構成案。手作業で約1時間かかっていたものが一言で出る
2. **FAQ作成**：AIが空想で質問を作らないよう、ラッコキーワードの「よくある質問検索」「集客コンテンツ検索（Yahoo知恵袋に絞る）」「関連KW（LSI/PAA）」「共起語」「見出し抽出（競合のFAQ）」で**実際に読者が聞いている質問**を拾う。回答ができたらWordPressのFAQブロックとして入稿
3. **公開前チェック**：誤字脱字の全文スキャン、表記揺れ、リンク点検、目次・ページ内ジャンプの整合、コピペ由来の不要タグ、画像のファイル名とalt。人より速くて正確
4. **WordPress入稿と装飾**：マーカー・ボックス・箇条書き・テーブル込みで入稿。比較表はスクリーンショットを渡せば同じデザインで作れる

## まだ任せられない4つ（人の比率）
| 工程 | 人の比率 | 理由 |
|---|---|---|
| 見出し構成 | 9割 | AIの構成は上位記事の真似＋要素の足し算になり、詰め込みすぎる。「読者が一番知りたいことは何か」「購入までどう話を進めるか」「見出しだけで内容が伝わるか」は自分の頭で組む。AI案は判断材料 |
| 本文 | 6割 | 情報や指示が少ないと「それっぽいけど何も言っていない文章」になる。「知識のデータベース」×「トンマナMD」で初稿の4割が生き残るまで改善 |
| リード文 | 10割 | 読者が読むか閉じるかを決める場所。検索意図で型が変わるのでルール化しにくく、自分で書く方が速い |
| セールスライティング | 9割 | 「買う前の最終確認の記事」と「知らない人に提案する記事」で訴求と熱量が変わる。ニュアンスはまだ人 |

## 配布プロンプト（1）記事構成リサーチスキル（要旨）
「記事構成を作って」で発動。指定KWについて次のSTEPを順に実行し、スプレッドシートにまとめる。
- STEP1 検索意図の深掘り：顕在ニーズ5〜7個（読者の一人称のセリフで）、潜在ニーズ5個、読者のゴール3個、NGパターン5個
- STEP2 KW収集：サジェスト・関連KW・共起語・質問系の4種類を検索ボリュームつきで。**数字はツールの実データのみ、AIの推測禁止。絞らず全件、取捨選択は人**
- STEP3 競合分析：上位10サイトのタイトルとH2/H3を一覧にし、共通トピック（5サイト以上＝必須）、足りないトピック（差別化チャンス）、不要な見出しを分析。**日本のGoogleの実際の検索結果を使う**
- STEP4 タイトル10案：メインKW左寄せ・30字前後、各案に狙い。数字・感情ワード・競合にない切り口
- STEP5 H2/H3構成：読者が一番知りたい答えを最初のH2に、足りないトピックを入れる、FAQのH2を終盤に、H3は疑問形より結論の言い切り
- **厳守：構成ができても本文は書かない。人が確認・修正して「本文GO」と言うまで待つ**（飛ばすと直すのが大変な長文が出る）

## 配布プロンプト（2）トンマナMD（要旨）
自分の文体ルールをまとめたファイル。執筆前に必ず全部読ませる。最初から完璧に埋めなくてよい。
1. 基本の文体：一人称、です・ます、NG語尾
1-2. 読みやすさ：一文60字以下、読点は1文2個まで、1段落2〜4文、同じ語尾を3回続けない、体言止めは段落末に1回まで、漢字をひらく（事→こと、時→とき、物→もの、下さい→ください、出来る→できる、是非→ぜひ）、削れる言葉を削る（〜することができます→〜できます）、あいまい語を数字に、「そして」「また」を連発しない、3つ以上並んだらリスト
2. 組み立て（PREP）：結論1文→理由→体験や数字→行動提案。見出し直下の1文目はそのセクションの結論
3. **AIのクセ禁止リスト**：情報量ゼロのつなぎ文（「ひとつずつご紹介しますね」）、章末の気の利いたまとめ文、装飾的な副詞（ぐっと・きっと・大きく左右します）、主語のない文（「1つ目は〜」「これで〜」だけ）、指示語（これ・それ・この）は具体名詞に
4. 語彙置換表「AIが書きがち → 私ならこう書く」：差分学習で育てる。最初は空でよい
5. 体験談：実在するものだけ、創作禁止。「不安だった→やってみた→解消した」の流れ

## 配布プロンプト（3）差分学習（要旨）
トンマナMDを記事ごとに育てる。記事の流れの最終ステップに組み込み、直し終えたら「差分学習して」と言うだけ。
1. AIに初稿を書かせる → 2. 自分で直す → 3. 初稿と最終版の差分をAI自身に分析させる → 4. 「AIが書きがち→私ならこう書く」のルールをトンマナMDに追記 → 5. 次の初稿から反映
分析プロンプトの要旨：削られた・書き換えられた箇所を全部リストアップ／なぜ直されたかを推測／繰り返し使えるルールの形にしてトンマナMDの該当セクションへの追記文面を提案／**初稿生存率**（初稿の何%が最終版に残ったか）を概算。ゴールは「次回から同じ修正を人にさせない」
- チャットで「やめてね」と注意しても直らない。**ファイルに書かせて初めて次回に引き継がれる**
- 初稿生存率を毎回メモし、上げることをAIと共有する

## まとめ
- AIがあっても「読者の悩みを解決する」軸は変わらない
- 記事を書く前にリサーチをする。「自分が書きたい記事」「書ける記事」ではなく「読者が知りたい記事」
- 記事を作れること自体にもう価値はない。AIには作れない一次情報（体験談・独自の視点）が価値。書く作業は効率化し、読者の役に立つ情報を見つけることに時間をかける
